# 資料攝入器（服務藍圖）

> **類型**：藍圖（服務）
> **焦點**：這個服務對系統其他部分的承諾，以及它依賴什麼。
> **限制**：只寫現況。不寫檔案結構、函式庫或實作（看程式碼庫）。不寫欄位層級的形狀（看合約檔）。不寫理由（看[決策日誌](safechord.safezone.decisions.md)）。不寫沿革（看 [changelog](safechord.safezone.changelog.md)）。

## 1. 職責

*   **角色**：Gateway / Producer
*   **核心目標**：作為病例資料的單一入口。把每個被接受的 HTTP 請求轉成 Kafka 上的一筆病例事件，讓突發流量由 topic 吸收，不會直接打到資料庫。

## 2. 需求

每條需求都是系統其他部分會依賴的承諾。守住某條需求的測試會帶上它的 ID。所有服務共用的需求放在[服務標準](safechord.safezone.service.standards.md)，這裡不重複。

### ING-R1：被接受的紀錄成為一筆事件
對每個被接受的請求，攝入器必須恰好發布一筆事件到病例事件 topic，日期、城市、區域與病例數原封不動。

#### 情境：有效紀錄
- GIVEN 一個帶有有效紀錄的請求
- WHEN 攝入器接受它
- THEN topic 上有一筆日期、城市、區域與病例數相同的事件

### ING-R2：發布的事件符合事件合約
攝入器發布的每一筆事件都必須符合事件合約。這是 STD-R4 在病例事件上的應用。

#### 情境：以合約檢查事件
- GIVEN 任何被攝入器接受的紀錄
- WHEN 用合約檔驗證由它建立的事件
- THEN 驗證通過

### ING-R3：同一城市與區域的事件共用一個鍵
同一城市與區域的事件必須帶有相同的 message key；不同城市或區域的事件必須帶有不同的 key。

#### 情境：相同的城市與區域
- GIVEN 兩筆城市與區域相同、日期不同的紀錄
- WHEN 兩筆都被發布
- THEN 兩筆事件帶有相同的 message key

### ING-R4：回報成功代表 topic 已收到事件
攝入器必須在 topic 確認收到事件之後，才對該請求回報成功；無法發布時必須回報失敗。

#### 情境：topic 無法連線
- GIVEN 攝入器連不上 topic
- WHEN 一筆有效紀錄到達
- THEN 請求失敗
- AND 呼叫端不會被告知資料已發布

### ING-R5：無效紀錄被拒絕，且不發布任何東西
攝入器必須拒絕違反攝入請求規則的請求，且不為它發布任何事件。

#### 情境：日期無效的紀錄
- GIVEN 一個日期不是日曆日期字串的請求
- WHEN 它到達
- THEN 請求被判定無效而拒絕
- AND 沒有事件被發布
