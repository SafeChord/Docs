# KDD 2.0 實務：雙引擎與無頭開發模式

SafeChord 的開發跑在 **「雙引擎」** 模型上：人類坐架構師席，兩個 AI 席位則依「失敗會不會自己叫」來分工。

---

## 1. 雙引擎模型

### 1.1 席位

| 角色 | 能力要求 | 當前載體 | 核心職責 |
| :--- | :--- | :--- | :--- |
| **🏛️ 架構師** | — | **人類** | **策略與取捨**：優先序、技術選型、做什麼以及為何要做。 |
| **🛡️ 開拓者** | 實作產出量；錯誤由測試攔截 | Claude Code · **Opus 5 / medium effort** | **實作與問題解決**：程式碼、Spike、複雜除錯。 |
| **🧠 維護者** | Repo 理解力與長流程專注度；沒有別的東西會攔下它的錯 | Claude Code · **Opus 5 / high effort** | **審查與鞏固**：測試規劃、程式碼審查、文件對齊。 |

**能力要求是契約，當前載體是實作細節。** 換掉載體不需要動到席位定義。前一版把席位綁在產品名上，當該產品停止服務時，角色定義沒有任何欄位會變紅——這場停機因此被忽略了三個月。

### 1.2 席位為什麼這樣切

拿到較強配置的是審查，不是實作。這推翻了「實作才是難的那一半」這個直覺。

| | 可執行的 oracle | 失敗型態 | 後果 |
| :--- | :--- | :--- | :--- |
| **實作** | 有——測試、程式跑不跑得起來 | 響亮、立即 | 較弱的配置撐得住，錯誤會自我回報 |
| **審查／文件對齊** | 沒有 | 靜音、數週後才浮現 | 必須用當下最強的配置 |

實作錯誤會撞上 `safechord.kdd.introduction.md` §3 所說的 **物理紅牆 (Physical Red Walls)**。審查沒有對應的牆，模型本身就是唯一的防線。

> **這個二分法是簡化過的。** Oracle 攔得到「跑不跑得起來」，攔不到架構走偏、重造一個已經存在的 utility、或跨 repo 契約被悄悄改掉。實作也有靜音失敗，而且集中在 repo 理解這一維——所以開拓者席降的是 effort，不是 model tier。

### 1.3 審查跑在自己的 session

**程式碼審查不得與它所審查的實作共用同一個 session**——即使兩個席位跑在同一個產品上。

理由與模型強弱無關：共用 context 的審查會繼承實作者的盲區。一個剛寫完某段程式的 session，正是最沒有資格審查它的 session。這讓「刻意輪替 session」從個人習慣升格為協定要求——見 §2 的交接觸發條件。

**這條要求只涵蓋審查，不延伸到維護者的其他職責。** 乾淨的 context 在不同任務上作用方向相反：

| 任務 | 乾淨的 context 是 |
| :--- | :--- |
| 審查一份實作 | **資產**——審查者不會繼承作者的假設 |
| 把已定案的決定對齊進 SSOT | **負債**——這是忠實轉寫，而一個得先重新推導「當初是什麼意思」的 session 會帶來漂移 |

文件對齊不是一次檢查。判斷在決定定案之前就完成了，且經過架構師審查。對齊欠的是忠實度，而忠實度由持有該決定的 context 來交付會更好。

## 2. 溝通介面與協定

在無頭環境中，標準化的協定對於代理之間資訊交換至關重要。

### 🟢 基本溝通：Git Commit 協定
對於無需正式交接的例行迭代，**Git Commit 訊息** 是代理與人類之間的橋樑。
*   **原則**: 訊息必須包含「意圖」與「架構影響」。
*   **格式**: 嚴格遵循 [Conventional Commits](https://www.conventionalcommits.org/)。
*   **代理義務**: 維護者審查的是掛在某張票底下的所有 commit。票出現之前，這件事只能從 commit 歷史去推論；現在它是一次查詢。

### 🔴 交接協定（Legacy 筆記）
*   **媒介**: 存放在 `.ai-session-handoffs/` 的 Markdown 檔案。
*   **對象**: 下一個 session，或另一個代理。**兩者是同一件事**——工作在一個不包含當前脈絡的 context 裡繼續。
*   **觸發條件**: 兩類，兩類都必須被承認。

    **被動觸發**——外部因素迫使移交：
    - 開拓者完成一個 Spike 或開發階段。
    - 代理遇到其操作範圍外的錯誤。
    - 人類介入要求任務移交。

    **主動觸發**——刻意結束這個 session：
    - Context 已經長到開始劣化，該換一個乾淨的 session 接手。**這是實務上最頻繁的觸發條件**，而且通常是同一個代理換新 session，不是換代理。

*   **充分性測試**: 筆記要帶走的量，必須足以讓「丟棄當前 context」這件事是安全的。不是完整的紀錄——是充分的紀錄。
*   **必要內容**:
    1.  **狀態/摘要**: 日期、方向（From/To）、分支狀態與進度。
    2.  **變更內容**: 檔案路徑與核心結構變更。
    3.  **驗證路徑**: 哪些方法已證明可行？（對死結交接尤為重要）
    4.  **未驗證／不確定**: 哪些是假設但沒查過的？作者對什麼沒把握？
    5.  **後續行動**: 對下一個代理的明確指示與驗證標準。

> **⚠️ 這份筆記由誰寫。** Legacy 筆記本質是有損壓縮——把整個 session 擠進數百字。當觸發條件是 context 劣化時，這份筆記由狀態最差的 session 產出，而它漏掉的東西永遠不會被發現。這是靜音失敗的教科書案例。
>
> 三個緩解手段，由便宜到貴：(1) 上面的 **未驗證／不確定** 欄位，強迫盲區被說出來——它補的是「已驗證」與「已知死路」之間的空缺；(2) 定期 checkpoint，而不是撞牆才寫；(3) 讓一個乾淨的 session 從票底下的 commit 與 diff 反推狀態，而不是信任舊 session 的自述。第三項要等票出現、能界定「該讀哪些 commit」之後才可行。

> **額度上的意義**：Context 膨脹會推高每一輪的 input token，是週額度最無聲的漏水點。輪替 session 是成本控制手段，不只是品質衛生。

### ⚪ 設計草稿
對於策略性決策或複雜重構，**設計草稿** 作為開拓者的藍圖。
*   **媒介**: 存放在 `.ai-session-drafts/` 的 Markdown 檔案。
*   **必要內容**: 背景、建議方案、藍圖（模擬程式碼/綱要）、取捨與後續步驟。

## 3. 雙軌工作流程：KDD 的平衡

SafeChord 採用基於標籤的 **雙軌工作流程**，以平衡「文件優先」的嚴謹性與「Spike 優先」的靈活性。

### 3.1 判別式在後端

兩條路徑**不是**用「動工前規劃了多少」來分的。分界只有一個問題，而且開票當下就答得出來：

> **`Docs/` 裡已經有這塊的藍圖了嗎？**

這個答案決定了文件對齊**是什麼**——一次查核，還是一次著作。

| 路徑 | 動工前有藍圖 | 文件對齊是 |
| :--- | :--- | :--- |
| `kdd:forward` | 有 | **查核**——確認程式符合規格；有偏差則修規格 |
| `kdd:spike` | 沒有 | **著作**——把結果寫回成一個新的 SSOT 節點 |

> **寫了設計草稿不會讓任務變成 `kdd:forward`。** 路徑 B 步驟一本來就會產出一份。草稿持有的是「一個尚未做出的決定」——是假說，不是契約。「沒有文件限制」指的是動工前 `Docs/` 沒有程式必須遵守的藍圖，從來不是「不准先寫任何東西」。

### 3.2 票（Ticket）

**兩條路徑都要開票**，在實作開始之前。它有三個作用：

1.  **臨時身分證**：Spike 探索的是知識樹上還不存在的節點，動工時沒有 `doc_id` 可以當錨點。票填補這段知識真空期，直到文件對齊把它結算成一個 `doc_id`。
2.  **開發足跡**：`doc_id` 記錄最終狀態，ADR 只記錄成功的那條路，commit 太細碎，Legacy 筆記只在例外時觸發。**「一件事從開始到結束」沒有別的容器。** `safechord.kdd.introduction.md` §4 承諾每一次調整都留下軌跡，票就是缺掉的那層粒度。
3.  **代理切點**：一個橫跨 session 的穩定容器。一張票可以收集多份 Legacy 筆記——**票是容器，交接是接力棒。**

**關票條件，兩條路徑一致：文件對齊完成。** 票的壽命因此等於「一份知識從未定到進入 SSOT」。

沒有文件影響的變更——CI 版本升級、路徑修正、相依套件雜務——不貼 `kdd:` 標籤，跳過文件對齊，合併即關票。

> **標籤的工作是告訴開拓者「有沒有規格要遵守」**，不是預測難度。`kdd:forward` → 先讀藍圖，照著實作。`kdd:spike` → 別去 `Docs/` 翻，翻了也是空的。
>
> 開票時貼的標籤是猜測。維護者在文件對齊時會知道真相：一張 `kdd:forward` 的票如果最後藍圖被改寫了，它其實是 spike。**翻轉率本身就是一個量測值**——量的是知識樹實際上有多成熟。標籤的價值來自它可被推翻，而不是來自它貼得準。

### 🟢 路徑 A：`kdd:forward`（有序模式）
應用於現有模組的最佳化與已知架構的延伸。
**規則**: 「先文件後程式碼」——沒有更新後的藍圖，不得進行實作。

1.  **策略設計**: 架構師定義「Why/What」；維護者更新 Markdown 知識地圖（藍圖/ADR）。**開票並標記 `kdd:forward`。**
2.  **實作**: 開拓者先讀藍圖，再嚴格在定義的邊界內實作程式碼與測試。
3.  **完成**: 開拓者提交 PR 並產生 Legacy 筆記。
4.  **鞏固**: 維護者根據預先定義的文件進行程式碼審查，合併並標記版本。**文件對齊在此是一次查核；程式有偏差就修藍圖，然後關票。**

### 🔴 路徑 B：`kdd:spike`（前線模式）
應用於新技術整合、未知錯誤修正或效能壓力測試。
**規則**: 「先程式碼後文件」——原型開發優先於文件。

1.  **策略設計**: 架構師討論可行性；若需要程式碼庫狀態，維護者建立設計草稿。**開票並標記 `kdd:spike`。**
2.  **Spike**: 開拓者在沒有藍圖需要遵守的情況下實作 Demo/Spike。
3.  **完成**: 開拓者提交 PR 並產生詳細的 Legacy 筆記。
4.  **鞏固**: **關鍵階段。** 維護者執行 PR 審查並進行**文件對齊**，將 Spike 結果逆向工程回 `Docs/` 中的單一事實來源（SSOT）。**把票結算成 `doc_id` 並關票。**

> **⚠️ 目前還沒有強制點。** 沒有東西會要求你貼標籤，也沒有東西會要求代理去讀它。依 KDD 層的規範，一條沒有觸發器的約束不會執行。這兩個標籤是刻意「先跑、後裝儀表」的——如果一個週期跑完沒有任何可觀察的效果，結論是這個訊號需要被寫進 `.ai-rules.md`，而不是這個訊號沒用。

## 4. 無頭協作規則

*   **終端機作為 SSOT**：所有開發與測試都在 CLI 中完成。IDE 僅供視覺審查使用。
*   **審查即文件**：維護者的審查核准隱含表示文件對齊已同步。因此**一張關不掉的票，就是文件債務的可見度量**——漂移不再是靜音的。
*   **上下文效率**：代理需善用其龐大的上下文視窗進行跨服務影響分析，以防止 API 合約中斷。

## 5. 操作範本（附錄）

### 🟢 Git Commit 範本
```text
<type>(<scope>): <subject> (最多50字)

[Body: 為何需要這項變更？]
說明動機與邏輯。專注於「Why」而非「How」。
描述對專案架構或長期決策的影響。

Context: [票號，或連結至藍圖]
Impact: [對 API 合約或基礎設施的具體影響]
Test: [執行的驗證方式] (例如：make test-data-ingestor)
Agent: [開拓者 / 維護者——若非預設載體則註明]
Legacy: [留待下一個代理處理的待辦事項]
```

### 🔴 交接範本（Legacy 筆記）

`From` / `To` **同時**帶席位與 session。最常見的交接是同一個席位、新的 session，範本必須講得出這件事。

```markdown
# 📝 Legacy Note: [Task Name]

> **Date**: YYYY-MM-DD
> **From**: [Seat] / [session id or descriptor]
> **To**: [Seat] / [new session]
> **Trigger**: [Reactive: milestone | blocked | human handover] or [Deliberate: context degradation]
> **Ticket**: [Ticket ID]
> **Branch**: [Branch Name]
> **Action Required**: [Brief summary]

---

## Status / Summary
[Complete / Partially Complete / Deadlock]

## What Changed
[Structural changes or architectural adjustments]

## Verified Path (Optional)
- [x] What has been proven feasible?
- [ ] Known dead ends or blockers?

## Unverified / Uncertain
- [ ] What was assumed but never checked?
- [ ] What is the author unsure of?

## Next Actions
1. [Specific Instruction 1]
2. [Specific Instruction 2]
```
