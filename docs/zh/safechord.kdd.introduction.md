# 知識驅動開發 (KDD)

SafeChord 不僅是一個軟體專案，更是一場關於 **「如何在 AI 時代建構軟體」** 的架構實驗。我們採用的核心方法論稱為 **KDD (Knowledge-Driven Development，知識驅動開發)**。

---

## 1. 典範轉移：什麼是 KDD？

過去，開發流程是「人類先寫程式碼，有時間再補文件」。

在 AI 的程式碼生成能力已迅速超越人類實作速度的時代，KDD 徹底翻轉了這個模型：

> **「程式碼是知識的產物，文件才是源頭。」**

KDD 是一套 AI 原生開發哲學，它將結構化的 **知識 (Knowledge)** 與 **意圖 (Intent)** 視為開發的起點與主要引擎，重新定義了人機協作的邊界。

---

## 2. 核心轉變：從「微觀規格」到「高層知識」

為什麼在 AI 時代我們要擺脫傳統的 Spec-Driven 開發？

*   **微觀管理扼殺 AI 潛力**：傳統規格如同施工手冊，鉅細靡遺地指定實作細節。現代前沿 AI 模型往往比撰寫規格的人類更了解演算法與實作模式；用低階指令限制它們，等於把一位資深合作夥伴降級成打字機。
*   **知識是活的，規格是死的**：KDD 放棄告訴 AI「如何做」，而是提供 **「什麼事」**（我們面對的真實問題）、**「為什麼」**（架構意圖），以及 **「脈絡」**（過去的嘗試與失敗原因——ADR）。
*   **賦能 AI 實作**：在 KDD 中，人類扮演架構師與指揮官，提供最完整的「背景知識」與「脈絡」。AI 代理取得這些知識後，便能自由找出最佳的實作路徑。

---

## 3. 核心約束：TDD 作為「收斂邊界」

如果我們給予 AI 最大限度的實作自由，要如何防止它「暴走」？

*   **沒有邊界的 AI 是一場災難**：給強大的代理工具一個模糊目標，往往導致無窮發散、幻覺功能與多餘的重構。
*   **從「品質保證」到「收斂機制」**：在 KDD 之下，**測試驅動開發 (TDD)** 發生了質變。測試不再只是為了防止缺陷，而是引導 AI 收斂的 **「物理紅線 (Physical Red Walls)」**。
*   **意圖在文件，規格在程式碼**：這是一個關鍵區別。在 Markdown 知識地圖中，我們只保留 **Why**、**What** 以及 **架構決策記錄 (ADR)**。而最終的詳細 API 合約 (Schema) 與具體測試案例，則完全存在於 **程式碼庫**（實際程式碼與測試檔案）中。
*   **分層 SSOT 邊界**：上述原則依不同層次有不同的應用方式：

    | 層次 | 文件是 SSOT 負責的項目 | 程式碼庫是 SSOT 負責的項目 |
    | :--- | :--- | :--- |
    | **App (命令式)** | 業務需求 (Why/What)、ADR | 端點 (Endpoints)、結構 (Schemas)、測試案例 (How) |
    | **Infra (聲明式)** | 設計約束（預算、延遲目標、容量上限）、架構原理 (Why this topology) | Manifest、Helm values、當前部署狀態 |

    在命令式的應用程式碼中，程式碼告訴你 *How*，但隱藏了 *Why*——因此文件要補足這個缺口。而在聲明式基礎設施 (GitOps) 中，**Manifest 本身就表達了意圖**（預期狀態）。此時，文件扮演不同的角色：將散落在數十個 YAML 檔案中的 *設計約束與跨層原理* 整合成一篇可讀的敘述。文件不重複 Manifest 的值，而是定義這些 Manifest 必須遵循的 **「紅線」**（成本上限、延遲目標、可用性需求）。

*   **測試程式碼作為邊界**：我們要求 AI 針對每個功能在程式碼庫中建立並通過對應的自動化測試。這等於告訴 AI：「無論你的實作多麼有創意，最終都必須滿足這些測試。」這將 AI 的幻覺鎖定在可執行的邊界內，同時避免文件變成雜亂無章、難以維護的規格說明書。

## 4. 物理載體：為什麼選擇「知識地圖」而非「向量資料庫」？

雖然用於 RAG 的向量資料庫很流行，但 KDD 堅持使用 Markdown 檔案與實體目錄樹結構（**Knowledge Map**）。這與 Andrej Karpathy 的「LLM Wiki」概念不謀而合：

*   **確定性 vs. 機率性**：向量資料庫將知識分塊，依賴機率的「語意相似度」。這往往導致 AI「重新發現」知識，或將不相關的模組混在一起，造成「檢索遺失」。相反地，KDD 使用 [**Knowledge Tree (`knowledgetree.md`)**](safechord.knowledgetree.md) 作為全域路由器。父子關係與模組依賴是 **絕對的**。
*   **複合知識**：KDD 的 Knowledge Tree 不是靜態的；它是一個隨著時間增值的持久產物。每一次 PR 與架構調整都會留下交叉參照與版本化邏輯的痕跡。
*   **消除繁重的維護工作**：過去人類難以維護大型 Wiki，因為連結與狀態更新需要大量勞力。在 KDD 中，人類做出高層決策（架構師），而 Markdown tree 的維護與文件對齊這類勞動密集型工作，則由從不疲倦的 AI 代理（維護者們，Settlers）負責。
*   **工具無關的適應性**：AI 工具演進迅速。SafeChord 已從網頁聊天介面轉向 API 呼叫，再到如今的雙軌 CLI 代理。這個轉換之所以順暢，正是因為 **Markdown 檔案是終極的工具抽象層**。

## 5. 動態平衡：雙向演化模型

如果盲目教條化地堅持「文件 ➡️ 程式碼」，會在技術探索 (Spike) 時扼殺靈活性。KDD 透過雙向模型維持平衡：

*   **戰略順序 (正向：文件 ➡️ 程式碼)**：對於優化現有模組或擴展現有架構，「文件優先」是鐵律。Markdown 知識節點就像法律框架，約束 AI 的實作邊界。
*   **戰術自由 (Spike：程式碼 ➡️ 文件)**：對於未知的技術探索，我們允許「程式碼優先」。我們給 AI 探索極限的特權。一旦 Spike 完成，結果必須被逆向工程回知識樹中，這個過程稱為 **「文件對齊 (Documentation Reconciliation)」**。

這並非對 KDD 原則的妥協，而是系統的「呼吸」——吸入高層意圖以定義邊界，呼出經過驗證的實作事實回知識庫。
