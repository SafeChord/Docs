# SafeZone 決策日誌（大腦）

> **類型**：大腦（決策日誌）
> **焦點**：每個決定為什麼這樣做，以及它放棄了什麼。
> **限制**：只寫理由。服務現在必須做到什麼，寫在它的藍圖。某個版本改了什麼，寫在 [changelog](safechord.safezone.changelog.md)。

## 這份日誌怎麼運作

*   **只增不改。** 已接受的條目不再編輯。決定改變時，新增一條，並把舊條目的狀態設為 `被 ADR-NNN 取代`。舊條目只有這一行狀態會變。
*   **單一編號序列。** 條目從 `ADR-001` 起，在整份日誌內依接受順序往上編號。編號不重複使用。
*   **依服務分章。** 每條放在它所屬服務的章節。約束一個以上服務的決定放在「跨服務」。
*   **由日誌指向需求。** `影響` 列出這個決定所塑造的需求 ID。藍圖不指回來。
*   **匯入的條目。** ADR-001 到 ADR-021 於 2026-10-07 從各服務藍圖搬來，保留原本的文字與版本標記。

## 跨服務

### ADR-024：共用合約是語言中立的檔案，以 unit test 驗證
*   **版本**：v0.3.8 · **狀態**：已接受
*   **影響**：STD-R3、STD-R4
*   **決策**：由一種以上語言使用的合約只定義一次，放在 `SafeZone/utils/contract/` 底下，格式為語言中立的檔案。每個服務用 unit test 對著該檔案驗證自己的實作。不從合約產生 model。
*   **原因**：病例事件原本有三份手動維護的版本（JSON Schema、Python model、Go struct），在三個欄位上互相矛盾，而且沒有任何東西發現。資料表只以 Python 程式碼定義，Go worker 讀不了，它的 SQL 是手抄的。兩者的根源相同：從來沒有決定合約要怎麼跨越語言邊界。不採用程式碼產生，是因為合約檔已經存在，缺的只是使用者，而且攝入請求的 model 同時是帶有自訂錯誤訊息的 HTTP 請求模型。決定於 SafeZone#70。

### ADR-025：病例事件合約記錄線上實際的格式
*   **版本**：v0.3.8 · **狀態**：已接受
*   **影響**：ING-R2、WK-R1
*   **決策**：`covid_event.json` 修正為符合資料攝入器現在實際送出的內容。`version` 是合約版本。Worker 暫時不依 `version` 做任何判斷。
*   **原因**：攝入器是這個 topic 唯一的生產者，它的輸出就是線上的格式；讓檔案對齊它，不需要改任何 production code。只有一個版本存在時，worker 的版本檢查不會有任何效果，而遇到不支援的版本該跳過還是停下來，目前沒有實例可以據以決定。決定於 SafeZone#70。

### ADR-026：資料表定義維持以 Python 為源頭，另外匯出 SQL
*   **版本**：v0.3.8 · **狀態**：已接受
*   **影響**：STD-R3
*   **決策**：`utils/db/schema.py` 維持為資料表定義的源頭。它的 SQL 匯出作為語言中立的產物提交，並有測試在兩者不一致時失敗。
*   **原因（取捨）**：改以 SQL 為源頭會換掉資料庫的初始化方式，並在 SafeZone#64 正在修改 worker 持久化程式碼的同時重寫它。匯出只花一小部分成本，就讓其他語言有東西可以對著驗證。源頭仍是單一語言的實作，照 ADR-024 這是一個缺口；方向留到 v0.4.0 重新檢視，屆時 schema 本來就會變動。決定於 SafeZone#70。

### ADR-027：Python scaffold 不再作為文件標準
*   **版本**：v0.3.8 · **狀態**：已接受
*   **影響**：STD-R1、STD-R2
*   **決策**：Python Microservice Scaffold 文件封存。其中的 trace 與 health 標準移到服務標準。工程原則（測試先行、注入依賴、業務邏輯不依賴框架）移到 `SafeZone/.ai-rules.md`。目錄結構、分層規則與 Dockerfile 模式不再由文件規定。
*   **原因**：Scaffold 把程式怎麼寫規定到檔名的層級，等於把實作者的上限壓在文件作者的能力之下，而且 Go 的部分根本沒有人審得了。目錄結構也是 agent 直接從程式碼庫就讀得到的東西。把它留在 `Docs/`，代表每次結構重構都得先改文件。ADR-016、ADR-017、ADR-018 記錄的是已經發生的重構，維持原樣。

*   **版本**：v0.2.0 · **狀態**：已接受
*   **影響**：ING-R1

## Worker

### ADR-005：至多一次精簡策略
*   **版本**：v0.2.0 · **狀態**：被 ADR-022 取代
*   **影響**：無
*   **決策**：實作激進的 offset 提交策略，並搭配資料庫 Upsert。
*   **原因（取捨）**：優先考慮吞吐量而非嚴格的恰好一次語意。在 SafeZone 等非金融場景中，此取捨簡化了狀態管理，同時仍可透過上游重新播放來復原。

### ADR-013：批次優先持久化
*   **版本**：v0.2.5 · **狀態**：已接受
*   **影響**：WK-R7
*   **決策**：設定預設批次大小為 1000 筆記錄。
*   **原因**：單筆 SQL 插入是資料庫效能的主要瓶頸。將壓力從資料庫 IOPS 轉移至記憶體，使系統能有效處理模擬器爆發流量。

### ADR-014：Franz-Go 用戶端遷移
*   **版本**：v0.3.0 · **狀態**：已接受
*   **影響**：無
*   **決策**：從 `segmentio/kafka-go` 切換至 `twmb/franz-go`。
*   **原因**：更優越的效能與完整的 KRaft 協定支援，降低尖峰消費期間的 CPU 開銷。

### ADR-015：慣用 Go 重構
*   **版本**：v0.3.0 · **狀態**：已接受
*   **影響**：無
*   **決策**：以套件層級建構子與介面注入取代 Java 風格的工廠模式。
*   **原因**：簡化程式碼層次，符合 Go 慣例，大幅簡化單元測試中適配器的 mock。

### ADR-022：至少一次消費
*   **版本**：v0.3.8 · **狀態**：已接受
*   **影響**：WK-R3、WK-R4、WK-R5、WK-R6
*   **決策**：Offset 只在事件儲存之後提交，每次寫入提交一次；提交的位置跟隨最後讀到的事件，因此被跳過的事件也會被提交過去。取代 ADR-005。
*   **原因**：讀到就提交，當機時最多會遺失一個批次；而 rebalance 之後，已不再擁有該 partition 的消費者送出的提交，會把 group 的進度倒回去，留下永遠消不掉的 lag，並把 autoscaler 釘在高副本數。至多一次的行為其實是從第一版 worker 沿用下來的函式庫預設值，ADR-005 是事後寫來合理化它的。冪等的 upsert 已經讓重送無害，而且每次寫入提交一次，比每筆事件提交一次便宜。決定於 SafeZone#64。

### ADR-023：同一次寫入內以後面的事件為準
*   **版本**：v0.3.8 · **狀態**：已接受
*   **影響**：WK-R2
*   **決策**：同一次寫入內有多筆日期、城市、區域相同的事件時，保留最新的那一筆。
*   **原因**：跨寫入時 upsert 本來就保留最新的事件，但同一次寫入內原本保留的是第一筆，因此儲存結果取決於批次邊界落在哪裡。至少一次消費（ADR-022）在重送時會重新分批，結果不能因此改變。上游預期不會對同一個鍵送出不同的值；這是防禦性的保護，不是針對觀察到的資料。決定於 SafeZone#64。

### ADR-028：Worker 透過 HTTP 回報健康，判準是迴圈是否在轉
*   **版本**：v0.3.8 · **狀態**：已接受
*   **影響**：WK-R9、STD-R2
*   **決策**：Worker 跟其他服務一樣提供 `GET /health`。只要消費迴圈持續轉動就算健康，不看 lag，也不看 Kafka 與資料庫是否連得上。
*   **原因（取捨）**：Worker 當初是當成 event-driven 的消費者設計的，不是 API，所以沒有任何健康訊號，Kubernetes 分不出卡死的 worker 和正常的 worker。選擇 HTTP 端點而不是由 exec probe 檢查的心跳檔，是為了讓所有服務用同一種方式檢查，之後 metrics 也能共用同一個 port。健康狀態刻意不看 lag，那是 autoscaler 的事；也不看依賴：如果 broker 或資料庫連不上就讓檢查失敗，所有 worker 會同時被重啟，重啟後面對的還是同一個故障。代價是與依賴斷線的 worker 仍會回報健康，這種狀況會改以 lag 的形式顯現。決定於 SafeZone#71。

## Analytics API

### ADR-001：記憶體內靜態資料預載
*   **版本**：v0.1.0 · **狀態**：已接受
*   **影響**：API-R1、API-R2
*   **決策**：在啟動時將低頻資料（城市/區域對應、人口基準值）預載入記憶體。
*   **原因**：將複雜的 SQL JOIN 簡化為單純的事實表聚合，大幅提升查詢效能。

### ADR-006：回應快取
*   **版本**：v0.2.0 · **狀態**：已接受
*   **影響**：API-R5、API-R6
*   **決策**：對所有聚合端點實作基於 Redis 的回應快取。
*   **原因**：最小化 API 延遲，並在讀取密集的環境中為 PostgreSQL 提供防禦層。

### ADR-007：快取版本化與雪崩防護
*   **版本**：v0.2.0 · **狀態**：已接受
*   **影響**：API-R6、API-R8
*   **決策**：在 `@redis_cache` 裝飾器中實作基於 `asyncio.Lock` 的 Double-Check Locking。
*   **原因**：防止在快取未命中時多個請求同時擊穿資料庫所造成的「快取雪崩」。

### ADR-018：分層依賴注入
*   **版本**：v0.3.1 · **狀態**：已接受
*   **影響**：無
*   **決策**：將 `request.app.state` 存取方式替換為在 `api/dependencies.py` 中的顯式 DI。
*   **原因**：犧牲少量開發速度以換取顯著的可測試性，使 `services/` 中的業務邏輯能夠保持框架無關。

### ADR-019：純 ASGI Middleware
*   **版本**：v0.3.1 · **狀態**：已接受
*   **影響**：API-R7
*   **決策**：將 `TraceAndCacheMiddleware` 從 `BaseHTTPMiddleware` 遷移至純 ASGI 介面。
*   **原因**：解決 `ContextVar`（例如用於 `X-Cache-Status`）在多個任務群組間無法正確傳播的隔離問題，確保一致的可觀測性。

## Dashboard v2

### ADR-020：Nginx 解耦
*   **版本**：v0.1.0（dashboard-v2）· **狀態**：已接受
*   **影響**：DSH-R7
*   **決策**：我們從 `Dockerfile` 移除 `COPY nginx.conf`。正式環境的容器映像編譯 TypeScript，並把靜態檔案輸出到公開根目錄。設定檔 `nginx.conf` 必須由外部注入。
*   **原因**：採用這個做法，是為了同時支援本機開發（Docker Compose 唯讀 volume 掛載）與 Kubernetes 正式環境（ConfigMap 掛載），不必為不同環境重建或維護不同的 Docker 映像。

### ADR-021：TopCities 七日時間窗隔離
*   **版本**：v0.1.0（dashboard-v2）· **狀態**：已接受
*   **影響**：DSH-R4
*   **決策**：我們抽出專用的 React hook `useTopCities`，對所有城市聚合呼叫寫死查詢參數 `interval="7"`，完全繞過全域的 interval 狀態。
*   **原因**：這確保了系統需求：前十名排行榜永遠代表七日滾動聚合，避免使用者把主要趨勢圖切換到其他聚合區間時產生混淆。
