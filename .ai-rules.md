# Docs (Knowledge Base) AI Rules

This directory is the Single Source of Truth (SSOT) and Knowledge-Driven Development (KDD) hub for SafeChord.

## 1. Directory Structure

```text
Docs/
├── docs/         # Pages (§3). English is the source of truth (§2.3).
│   ├── zh/         # Traditional Chinese mirror (§2.3).
│   ├── blog/       # Case studies written for people.
│   ├── material/   # Static assets: images, diagrams, references.
│   ├── templates/
│   │   ├── page/       # Archetype scaffolds (§3.1).
│   │   └── protocol/   # Protocol templates (§4).
│   └── archive/    # Deprecated historical docs (cold storage).
├── overrides/    # Custom theme overrides for MkDocs.
├── hooks/        # MkDocs hooks; zh_stale.py also lists stale zh pages (§2.3).
├── zh-sources.json  # The en version each zh page was translated from (§2.3).
├── zh-glossary.md  # The terms a zh page uses (§2.3).
├── opencode.json # Limits opencode sessions started here to editing docs/zh/.
└── mkdocs.yml
```

## 2. Documentation Policies

- **SSOT Area**: The documentation here dictates the architectural and behavioral contracts for the entire system.
- **Divergence**: how a deviation between the code and a page here is settled, and by whom, is on the development page (`docs/safechord.kdd.practice.development.md` §1, and Solidification in §3.1).

## 2.1 Landing a Change

`main` is what every session reads and what the site deploys. An edit decided in conversation with the human, a ticket's reconciliation included, is committed by the agent straight to `main` and pushed. An alignment run lands as the alignment page's Landing says; a mode's work lands as its page says.

## 2.2 Links

- **Links target explicit ids.** A heading that any link points at carries an explicit id through `attr_list` (`### 3.2 Handling review findings {#32-handling-review-findings}`), the same id on the en and zh pages. Never link to an id MkDocs generates: it drops CJK characters and emoji, and an unnumbered heading's fallback id (`_1`) moves when a heading is added before it.
- **The build checks links.** `make build` runs MkDocs in strict mode, so any warning fails it, and the deploy workflow with it. A link from an en or zh page to a file that does not exist is a warning, and so is a link from an en page to an anchor that does not exist. Anchors on the zh site are not checked, because zh trails en (§2.3) and a stale zh page lacks the ids its en page has gained since. External URLs are not checked.

## 2.3 Languages

- **English is the source of truth; `docs/zh/` mirrors it.** A page directly under `docs/` has its zh page at the same filename under `docs/zh/`, at structural parity with the en version it was translated from: the same sections in the same order, with the same explicit heading ids, requirement IDs and ADR numbers. Where the two disagree, the en page wins.
- **zh trails en.** A change to an en page leaves its zh page as it is. `zh-sources.json` records, for each zh page, the git blob of the en page it was last translated from. A zh page is **stale** when it does not exist yet, when it has no entry there, or when its en page's text below the frontmatter has changed since that blob; `python3 hooks/zh_stale.py` lists the stale pages, and the site marks each stale zh page with a notice. A page with no zh page yet is served in English on the zh site.
- **zh is brought up to date by hand**, through the `translate` skill (`.claude/skills/translate/` in the workspace harness), which also updates the page's entry in `zh-sources.json`. A commit that brings a zh page up to date carries that entry in the same commit.
- **zh is written for people.** Agents read the en page, which wins any disagreement; the zh page serves people who read Chinese. It carries the same facts in the same structure, in natural Traditional Chinese, the way a Taiwanese engineer writes for peers. Numbers, years and version strings stay as the en page has them.
- **Form.** A space separates Chinese from adjacent Latin letters and digits (`SafeZone 生態系統`); punctuation in Chinese prose is full-width.
- **Terms** live in `zh-glossary.md`: what stays in English, the project's fixed translations, the general and technical terms, and the wording to avoid. A zh page uses them, and the translate skill's run reads that file with this section.

## 3. Writing a Page

This file is the one home for the rules a page directly under `docs/` follows. A page template under `docs/templates/page/` is a scaffold that follows this file; where the two disagree, this file wins and the template is fixed.

### 3.1 Archetypes

Every page has one archetype, declared in its `archetype` field, and starts from that archetype's page template where one exists.

- **An archetype comes before its page.** A page that fits none of the archetypes below waits until a new one is added to this list, with what it is for and what does not belong on it.
- **A page template comes after its pages.** An archetype can live without a template until two or more pages show its shape; the `align-full` scan asks then whether to induce one. A template written from a single page fixes that page's accidents as the rule.

- **Map** (`archetype.map.md`): navigation and aggregation (e.g., `safechord.knowledgetree.md`).
- **Blueprint** (`archetype.blueprint.microservice.md`): what a SafeZone service or toolkit component promises now. Requirements (one `SHALL` sentence plus Given/When/Then scenarios, each with a stable ID) and Dependencies (the channels it connects to, each pointing at its contract file). Current state only: edit by replacing. File structure, libraries and test file paths belong to the codebase, field-level shape to the contract files, reasons to the decision log, history to the changelog.
  - `safechord.safezone.service.standards.md` — requirements that bind every SafeZone service, and the index of shared contracts. A service blueprint links to it instead of repeating it.
- **Script** (`archetype.script.md`): workflows and standard operating procedures.
- **Brain** (`archetype.brain.md`): decision records and design principles.
  - `safechord.safezone.decisions.md` — the decision log for SafeZone and SafeZone-Deploy, grouped by service or area. **Append-only**: never edit an accepted entry; add a new one and mark the old one `Superseded by ADR-NNN`. Each entry lists the requirement IDs it affects; blueprints do not point back.
  - `archetype.brain.infrastructure.md` — infra-layer components (GitOps-managed): design constraints as red walls (budget, latency, capacity ceilings), strategy and policy, and reference snapshots (point-in-time, not SSOT). Manifest values stay in the manifests.
- **Changelog** (`archetype.changelog.md`): what changed, per version. `safechord.chorde.k3han.changelog.md`, `safechord.kdd.changelog.md`. SafeZone's changelog lives in its repository (§3.2). The KDD changelog also records, for each decision, what it replaced and what was rejected: the KDD pages state only the shape in force, so those alternatives have no other home.
- **Practice** (no page template): `safechord.kdd.practice.md`, the base every KDD mode page takes as given.

**Header.** Below its title, every page opens with the archetype contract's three fields (`~/.ai-agent/kdd.md` §4). Its **Type** is its archetype from the list above.

### 3.2 Where a Fact Lives

- **App (Imperative)**: Docs own Why/What. Codebase owns How (endpoints, schemas, test cases). The documents below split the Why/What, and one fact has one home:
  - **Service blueprint** — what must hold now. A promise belongs here only if something outside the service relies on it: if the implementation can change without anything outside noticing, it is not blueprint material.
  - **Decision log** — why. `ADR-NNN` identifiers exist only there, in one sequence.
  - **Changelog** (`SafeZone/CHANGELOG.md`) — what changed in a release and what was added, limited to what a user of the system needs to know. No reasons. It lives in the application repository and is kept with each release; Docs hold no copy of it, and a page that points at a release's changes links there.
  - **Contract files** (`SafeZone/contract/` and the other definitions indexed in the service standards) — field-level shape, and what counts as valid. They are SSOT of the same standing as a blueprint. They live in the application repository, not in `Docs/`, because the tests that enforce them load them at build time. A blueprint states that its service honours the contracts in its Dependencies table and points at them; it never restates what a contract allows, in a requirement or in a scenario.
- **Delivery** (SafeZone-Deploy and the delivery workflow): the reasons behind a delivery choice stay on the delivery page that makes it, the delivery workflow or the deployment map.
- **Infra (Declarative)**: Docs own design constraints and architectural rationale. Manifests own current deployed state. Docs consolidate cross-cutting context scattered across YAML files, but do not replicate specific values. Rationale stays on the brain page it explains.
- **A reason outside the decision log** sits beside the choice it explains, in a sentence or two of prose, with no record number: only the decision log numbers its entries. A reason that holds only while a condition does names the condition, so that the reader knows when to revisit the choice ("while schemas still break between releases"). A behavior that was observed but whose cause was not established is written as observed (§3.3).

### 3.3 Register

- **The reader is an agent that loads the page as context.** Write plain, declarative, present-tense prose: what holds, where it lives, and why where the archetype allows. Every sentence carries a fact or a rule the reader can act on.
- **One fact, one place.** Where another page owns a fact, link to it.
- **Unknowns are written down.** A gap, an untested assumption or an open decision is stated as one (`Not established`, `Not tested`, `Open decision`), so that silence never reads as confirmation.
- **Narrative for people goes to the blog** under `docs/blog/`, which keeps its own voice.
- For depth, the `writing-for-agents` skill (`.claude/skills/writing-for-agents/` in the workspace harness) covers single source of truth, caches, sediment and no-ops.

### 3.4 Diagrams

- **A diagram is the home of a structure.** Draw one when three or more things connect in a way prose would have to flatten: a topology, a data flow, a state machine. The prose beside it adds what the diagram cannot carry, such as reasons and limits, and leaves the edges to the diagram.
- **A sentence or a table carries everything else.** Diagram sections in page templates are optional.
- **Nodes and edges are facts.** When a fact a diagram shows changes, the diagram changes with it.
- Diagrams are Mermaid, inside the page.

### 3.5 Frontmatter

Every field has a reader. A field enters with the reader it serves; a field that nothing reads or checks is removed. A zh page carries no frontmatter: its en page's applies.

| Field | Pages | Read by |
| :--- | :--- | :--- |
| `title` | every page | MkDocs, as the page title |
| `status` | every page | the agent: `active`, `legacy` or `draft` says whether the page describes the running system |
| `archetype` | every page | the agent, to pick the rules of §3.1 |
| `code_paths` | pages that describe code | the agent, which lists these paths before reading the code |
| `app_version`, `doc_version` | blueprints | the forward path sets `app_version` to the ticket's milestone (development mode §3, Path A, step 1.2); `doc_version` is the field an editing agent bumps, so that `app_version` moves only with a milestone |
| `doc_version`, `last_updated` | the KDD practice and its development page | its adjustment notice, and the version headings of the KDD changelog |

### 3.6 When a Rule Here Changes

- **A rule about where a fact lives applies to every page at once**: a page left behind gives its reader a wrong fact.
- **A rule about form** (the header, the register, diagrams, frontmatter, a page template's sections) applies to a page the next time its content is edited. The `align-full` scan reports the pages not yet edited.

## 4. Subdirectory Access Rules

### `material/` — Static Assets
- **Ignore by Default**: Do not load unless the user explicitly asks to analyze a specific asset.
- **No Modification**: Do not alter files here unless performing an asset optimization task.

### `templates/page/` — Archetype Scaffolds
- **Scaffolding Only**: Read when creating a page, or when a page's content is edited and its form is brought in line (§3.6).
- **Context Exclusion**: Do NOT cite template content as architectural evidence — they are empty shells.
- **Follows §3**: A page template changes only to follow this file.

### `templates/protocol/` — Protocol Templates
- **Contract**: each file is the template of a protocol the KDD pages define, and states what each field a reader acts on can be taken as. Unlike a page template it is written before its uses, and it may be cited as a rule.
- **Layout**: the practice's shared protocols at the top, a mode's own in a directory named for the mode. Files are named for their artifact; the page whose protocol it is names which file a mode uses. A template that extends another holds only its additions.
- **Read by path**: the practice or the mode page points at the file, and so does a skill or a prompt that produces the artifact; the skill holds only how to fill it.

### `archive/` — Cold Storage
- **Ignore by Default**: Do NOT include archived files when building context for current tasks.
- **Lowest Priority**: If a conflict exists between `archive/` and `docs/`, `docs/` is SSOT.
- **Historical Context Only**: Reference only when the user asks about history, previous versions, or evolution.
